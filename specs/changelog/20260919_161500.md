## Update

`POST /api/v1/boards/:boardId/members` no longer rewrites an existing member's
role, and no longer accepts a role it cannot store.

The handler treated a duplicate add as an idempotent role update, with `role`
defaulting to `MEMBER` whenever the body's role was absent or not in
`VALID_ROLES`:

```ts
if (existing) {
  await db('board_members').where(...).update({ role, ... });
}
```

Two consequences. A board ADMIN could be silently demoted: `POST {userId}` with
no role on an existing admin rewrote their role to `MEMBER`, bypassing the
last-board-admin guard in `members/update.ts` and leaving a board with no admin
at all — the exact state that route refuses to create. And `observer` was
swallowed: `VALID_ROLES` holds uppercase `ADMIN`/`MEMBER` while the MCP
`invite_to_board` tool offers lowercase `member`/`observer`, so both fell
through to the `MEMBER` default and a caller asking for `observer` got a full
member with no error.

Changes in `server/extensions/board/api/members/create.ts`:

- A duplicate membership returns `409 board-member-exists` and performs no
  write, pointing the caller at `PATCH /api/v1/boards/:boardId/members/:userId`
  — the route that enforces the last-ADMIN invariant. The insert itself is the
  authority rather than a preceding read: `board_members` carries
  `UNIQUE (board_id, user_id)` (migration 0040), so a read-then-insert would let
  two concurrent adds both pass the check and surface PostgreSQL `23505` as a
  500. `onConflict(...).ignore()` makes the losing writer return zero rows,
  which is reported as the documented 409.
- `normalizeRole()`: an omitted role still defaults to `MEMBER`, a supplied role
  is upper-cased, and anything outside `ADMIN`/`MEMBER` is rejected with
  `400 invalid-role`.
- The success status is now always `201`; the `200` branch existed only for the
  removed update path.

`server/extensions/board/api/members/update.ts` now accepts an explicit board
`ADMIN`/`OWNER` as well as workspace `ADMIN+`, matching the policy POST already
applied. Callers are redirected here to change a role, so this route must not be
stricter than the one referring them; the last-ADMIN guard is unchanged.

Compatibility: `src/extensions/Board/components/BoardMembersPanel` already
filters existing board members out of its add candidates and always sends an
explicit uppercase role, so the UI cannot reach either new error. Callers that
used POST to change a role must switch to the PATCH route. The MCP
`invite_to_board` tool's `observer` option now returns a clear `invalid-role`
error instead of quietly granting MEMBER.

## New

- `server/extensions/board/api/members/__tests__/addBoardMember.test.ts` and
  `__tests__/fixtures/addBoardMember.ts` — regression coverage run in a
  subprocess with a faked db chain. Written RED first against the old handler:
  the duplicate, invalid-role and case-insensitivity cases all failed before the
  fix and pass after it. Covers insert-as-member, duplicate conflict, invalid
  role, `admin` accepted in any case, and the unchanged workspace-membership
  gate.
- `tests/db/concurrentBoardMemberAdd.ts` — a PostgreSQL-backed regression for
  the race the fake-DB tests cannot express: two adds fired together must yield
  one `201` and one `409`, with exactly one row in `board_members`. Verified to
  fail with a raw `23505` when the atomic insert is reverted to a
  read-then-insert.

## Technical Debt

None.

## What Should Be Done Next

- The MCP `invite_to_board` tool still advertises an `observer` role this route
  cannot store. Either add a board-level observer role or drop the option.
- That same tool sends `email` to a route that requires `userId`, so it cannot
  currently succeed. Fixed separately on `jaime-fix-invite-to-board-email`.
