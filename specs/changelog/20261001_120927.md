## Update

Copying a card now authorizes the destination as well as the source. When the
target list is on another board, the target board must exist, be ACTIVE, be in
the source card's workspace, be visible to the caller, and grant MEMBER-level
write access (workspace MEMBER+ or board guest MEMBER), all before any row is
inserted. Same-board copies are unchanged. The card, member and checklist inserts
then run in one transaction that first re-reads the target list `FOR SHARE`;
that conflicts with the row lock an `UPDATE` of `lists.board_id` takes (as
`PUT /lists/:id/idBoard` does) but not with the `KEY SHARE` other card inserts
take, so the list cannot be relocated between authorization and insert. With
`keepMembers` or `keepChecklists`, the workspace and target-board advisory locks
are taken before that row lock, in the order board and workspace deletes use
before cascading to lists.

Deleting a list now counts its cards and deletes it in one transaction holding
`FOR UPDATE` on the list row. A card insert into the list takes a foreign-key
`KEY SHARE` lock on that row (as does a move, which updates `cards.list_id`),
and that conflicts with `FOR UPDATE`, so a card can no longer land between the
confirmation check and the cascading delete. After taking that lock the handler
compares the list's board with the one it authorized; if `PUT /lists/:id/idBoard`
moved the list in the meantime, it refuses with 409 and deletes nothing. The
204/409 `delete-requires-confirmation` contract is unchanged.

## New

- Copy into another workspace returns 403 `cross-workspace-copy-forbidden`
  (the Copy dialog only offers same-workspace boards; Move already rejects it).
- Copy returns 409 `target-list-changed` (Move's code) when the target list was
  moved to another board after authorization; nothing is inserted.
- List delete returns 409 `target-list-changed` when the list was moved to
  another board after authorization; the list and its cards are kept.
- `tests/db/copyDestinationAndListDelete.ts` runs the real card and list routers
  against PostgreSQL: cross-workspace, PRIVATE without access, ARCHIVED and
  guest-VIEWER destinations are refused with no card inserted; authorized and
  same-board copies succeed; a copy racing an uncommitted relocation of its
  target list to another workspace waits, then returns 409 with no card; empty, unconfirmed and confirmed deletes keep their
  contract; an unconfirmed delete waits for an in-flight card insert and returns
  409; a card insert blocks on the delete's row lock and fails on the FK after
  commit; a confirmed delete racing an uncommitted relocation of the list to
  another workspace waits, then returns 409 and keeps the list and its card. It is wired into the PostgreSQL CI job with `CHIMEDECK_TEST_SANDBOX=1`.

## Technical Debt

Copy authorization is a preflight, like Move's preflight: the destination
list is pinned to the authorized board at insert, but board grants, visibility
and archive state are not re-checked under the advisory locks, so access
revoked while the copy waits is not re-checked. Re-authorizing inside the
transaction under the workspace/board advisory locks would close it.

A rare three-session deadlock is possible: a confirmed list delete holds the
list `FOR UPDATE`; a copy with `keepMembers`/`keepChecklists` holds the
workspace advisory lock and waits for that list `FOR SHARE`; a Trello-compat
cross-board card move out of the same list (`trelloCompat/api/cards/index.ts`,
around line 828) updates the card, then its 0123 trigger waits for the
workspace lock. PostgreSQL aborts one participant (500); no data is lost.
Trello card moves taking the same advisory locks as native Move first would
remove the cycle.

Move re-reads its target list without a row lock, so its card `UPDATE`
(`KEY SHARE` on the list) does not block a concurrent relocation either (the
gap this change closes for Copy). A missing target board is handled (404
`target-board-not-found`, as in Move) but is unreachable while `lists.board_id`
is a NOT NULL foreign key. The script exercises the insert lock; the move path
relies on the same foreign-key semantics and is not exercised. `keepMembers`
still copies card members without checking their eligibility on the target
board, and Copy into an archived target list is not refused (Move refuses it);
both predate this change and are untouched.

Validation on Bun 1.3.14: the new PostgreSQL script fails on the previous copy
and delete handlers (the list-relocation race fails with 204 instead of 409
without the moved-board re-check) and passes with this change; ESLint passes on the changed
files; `bun x tsc --noEmit -p .` reports the 143 baseline errors, none in the
changed files; `bun run build:client` passes.

## What Should Be Done Next

Review and deploy through the normal release process. Clients that copied cards
across workspaces through the REST API now receive 403
`cross-workspace-copy-forbidden`, which is stricter than before and matches the
Copy dialog (same-workspace boards only) and Move; the MCP `copy_card` tool in
PR #23 receives the same 403 for such lists.
