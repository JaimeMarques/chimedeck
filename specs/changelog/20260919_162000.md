## Update

`POST /api/v1/boards/:boardId/members` now accepts `{ email }` as well as
`{ userId }` to identify the target user. `userId` still wins when both are
supplied.

`server/extensions/mcp/tools/inviteToBoard.ts` posts to this route with a body
of `{ email, role }`, while the handler read only `body.userId`:

```ts
const { userId } = body;
if (!userId || typeof userId !== 'string') {
  return Response.json({ name: 'missing-user-id', ... }, { status: 400 });
}
```

Every call to the tool therefore failed with `400 missing-user-id`, no matter
how valid the email — the tool's own description, "Invite a user to a board by
email", could not be satisfied by any input.

Changes:

- `server/extensions/board/api/members/create.ts` — resolve the target user from
  `email` when `userId` is absent. The lookup joins `memberships` and is scoped
  to the board's workspace, so an unknown address and an address belonging to
  someone outside the workspace return an identical `422`: resolving globally
  first would let a board admin probe whether an arbitrary address has an
  account anywhere on the instance (404 vs 422). Matching is case-insensitive on
  both sides (`LOWER(u.email)`), because registration and OAuth store the casing
  the user supplied and `users.email` carries only a case-sensitive unique
  constraint — a stored `Mixed@Example.com` is still found by
  `mixed@example.com`.

  Because that uniqueness is on the raw casing, `Alice@example.com` and
  `alice@example.com` can both exist and both be eligible. Resolving one of
  them would be arbitrary and could grant board ADMIN to the wrong account, so
  the route selects all normalized matches and returns `409 ambiguous-email`
  when there is more than one, telling the caller to pass `userId` instead. It
  fails closed rather than guessing.

  With neither identifier the error stays `400 missing-user-id`, now worded
  "userId or email is required". Every check
  after identification — workspace membership, duplicate membership, role
  validation — is unchanged and applies identically to both paths.
- `server/extensions/mcp/tools/inviteToBoard.ts` — the role enum offered
  `observer`, which board membership does not have (`VALID_ROLES` is
  `ADMIN`/`MEMBER`); it is now `member | admin`, matching what the route can
  actually store.
- `server/extensions/mcp/README.md` and
  `src/extensions/DeveloperDocs/containers/McpDocsPage/McpDocsPage.tsx` — both
  advertised the old `"member" | "observer"` role pair and now match the tool.

Compatibility: purely additive for existing callers — a body with `userId`
behaves exactly as before, including the `missing-user-id` error name when
nothing is supplied. `src/extensions/Board/slices/boardMembersSlice.ts` sends
`userId` and is unaffected. Board invites still only reach people who already
have an account and already belong to the workspace; this does not create
accounts or workspace memberships.

## New

- `server/extensions/board/api/members/__tests__/addBoardMemberByEmail.test.ts`
  and `__tests__/fixtures/addBoardMemberByEmail.ts` — subprocess fixture.
  Written RED first (the email case returned 400 before this change). Covers
  email lookup, case and whitespace normalisation in both directions,
  `userId` precedence over `email`, a workspace GUEST being ineligible, the
  unchanged duplicate-member 409, and the neither-identifier 400. The
  unknown-address and outside-the-workspace cases assert an identical status
  **and body**, so the oracle cannot reappear.
- `server/extensions/mcp/tools/inviteToBoard.test.ts` — registers the real tool
  against a stub server and invokes the handler, asserting the request body sent
  to the route, the advertised role options, and structured error passthrough.
  Verified to fail when the enum is reverted to `observer`.
- `tests/db/addBoardMemberByEmail.ts` — the same route against real PostgreSQL,
  where the fixture only models the SQL. Two accounts differing solely by case
  are inserted so `LOWER(u.email)` genuinely matches two rows, and the add is
  refused; the outsider, workspace-GUEST and unknown-address cases are asserted
  to return an identical status *and* body. Verified to fail — returning 201 and
  adding an arbitrary twin — when the ambiguity guard is removed. Runs via
  `bun run test:db`.

## What Should Be Done Next

- Bringing in someone without an account still requires
  `POST /api/v1/workspaces/:id/invite` (or board guests). If inviting a stranger
  straight to a board is wanted, that flow needs to create the workspace
  membership too.
- `LOWER(u.email)` is not indexed, so this lookup cannot use the existing
  `users.email` index. A functional index on `LOWER(email)`, or a stored
  normalised column with a unique constraint, would make case-insensitive
  matching both fast and authoritative — and would stop case-variant accounts
  coexisting at all, at which point the `ambiguous-email` branch becomes
  unreachable and can be deleted. Until then this route fails closed instead of
  resolving a collision arbitrarily.
- `server/extensions/workspace/api/members/add.ts` still performs an exact
  lower-cased match and returns `404 user-not-found`, so it has the same
  case-sensitivity gap and its own existence oracle. Worth aligning in a
  follow-up.
