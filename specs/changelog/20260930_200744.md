## Update

Browser realtime now answers the server's application heartbeat, retires stale
connecting/half-open sockets, ignores retired socket callbacks, and cleans up
recovery timers on deliberate disconnect or forced logout. Board hooks adopt an
already-connected singleton, use current callbacks, and recover on tab/network
return. Healthy tab/online notifications and the initial socket open preserve
the progressive foreground load; only an actual recovery or replayed queued
mutation triggers a complete snapshot after open. Expired access tokens silently renew through the existing refresh-cookie
endpoint; HTTP and socket renewal share one request and adopt its fresh token.
Revocation and failed renewal still end the session, and logout cancels late
renewal without changing protected routes to a loading state.
Same-session renewal preserves board-switcher state and in-flight mutations.
Cookie-only HTTP recovery remains available until explicit logout/revocation;
only a new validated session re-enables recovery after that boundary.
Network/timeouts and server failures during renewal keep the session active and
retry renewal with capped backoff, activating polling after repeated failures.
Terminal auth failures and cancellation still end recovery. Board-only
subscriber replacement adopts the validated fresh token; a newer supplied token
takes precedence, and a cancelled renewal never reopens the expired token.
Same-session concurrent logout calls share one DELETE and cancellation scope.
A rejected logout response that retains auth restores recovery only for that
unchanged session, including both orderings of an already-cancelled socket
renewal. The old refresh generation remains invalid. Successful and local
network-failure logout keep their existing terminal behavior.
Repeated rejection of freshly renewed socket tokens before a validated server
pong uses independent one-to-thirty-second backoff and retains polling after
three bursts. A server pong or true session clear resets this throttle.

Board reconnect and polling fallback use the existing authoritative board fetch
instead of replaying history from an uninitialized event cursor. Background
refreshes preserve the last successful view on network failure, coalesce a
trailing recovery request, and discard superseded board responses and hydration
batches. Replayed list creation preserves existing card memberships.
Background snapshots fetch complete card membership, preserving lists with more
than one hydrated page. Live changes and active drags defer stale snapshots;
one cancellable retry timer reconciles at a five-second cadence after changes
settle. Foreground navigation retains ownership of its in-flight board fetch.
Snapshot polling fetches immediately on entering fallback, then every thirty
seconds; generic event polling retains its existing five-second interval.
Transient failed recovery GETs retry at the existing five-second cadence while
retaining the last view. Authentication/resource errors and aborted requests do
not loop. Healthy same-board HTTP token replacement also reconciles its brief
connection gap once after reopening.
An active same-board fallback also keeps polling through credential rotation
until the replacement socket is successfully connected.

## Technical Debt

The reported live browser idle sequence has not been reproduced against a
running application. Regression tests establish the demonstrated heartbeat and
list replay defects and the recovery behavior. Background recovery reads all
cards through the existing full-board endpoint, so large boards incur a larger
recovery response than the progressive initial load. Full project typecheck and
changed production file lint retain existing baseline failures; these gates are
not reported as green.
In HTTP fallback, updates can take up to thirty seconds to appear between
successful polls. Full snapshots remain larger than event batches; a lightweight
change probe would need a separately designed server cursor contract.
