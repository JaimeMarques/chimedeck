## Update

A board must always keep at least one ADMIN. Three writers could break that and
did not check: `PUT /1/boards/:id/members/:idMember` and
`DELETE /1/boards/:id/members/:idMember` in the Trello-compatibility adapter,
and the GUEST-conversion upsert in `workspace/api/members/add.ts`. The two
native routes checked, but not atomically.

`members/update.ts` and `members/remove.ts` refuse to demote or remove a board's
only ADMIN, returning `409 last-board-admin`. The Trello-compat adapter reaches
the same table with no such check:

```ts
// PUT /1/boards/:id/members/:idMember
const boardRole = memberType === 'admin' ? 'ADMIN' : 'MEMBER';
...
await db('board_members').where({ board_id: board.id, user_id: idMember })
  .update({ role: boardRole, ... });

// DELETE /1/boards/:id/members/:idMember
await db('board_members').where({ board_id: board.id, user_id: idMember }).delete();
```

`memberType` defaults to `'normal'` when the parameter is absent, so a bare
`PUT .../members/:id` demotes the target to MEMBER. Both routes are gated only
by `canWriteBoard`, which the last admin satisfies for their own board — so that
admin could demote or remove themselves and leave the board with zero admins.
`trelloCompatRouter` is mounted unconditionally in `server/index.ts`, behind no
feature flag. Once a board has no ADMIN, `members/update.ts` cannot promote
anyone back: promotion requires workspace ADMIN+ or an existing board admin.

Checking before writing is not sufficient on its own. Reading the admin count
and mutating in separate statements lets two concurrent demotions each observe
count = 2, conclude they are safe, and together empty the admin set. The guard
and the write therefore share one transaction, serialised per board with a
PostgreSQL transaction-scoped advisory lock keyed on
`hashtextextended(board_id)`. Different boards never contend, and the lock is
released when the transaction ends.

- `server/extensions/board/api/members/update.ts` and
  `server/extensions/board/api/members/remove.ts` — the inline copies now call
  `enforceLastBoardAdmin`, which performs the check and the write together.
  Same status, same error name, same messages.
- `server/extensions/trelloCompat/api/boards/index.ts` — both member routes run
  their read-modify-write inside the same enforced transaction.
- `server/extensions/workspace/api/members/add.ts` — promoting a workspace GUEST
  bulk-upserts `board_members` across every board in the workspace with
  `.merge({ role })`, which would overwrite a sole board ADMIN with MEMBER. Each
  board is now locked and evaluated; boards where the change would empty the
  admin set are skipped while the workspace promotion itself still proceeds.

Compatibility: the native routes see no behaviour change — identical statuses,
error names and messages. On the Trello-compat routes, a client that previously
demoted or removed a board's last admin now gets `409`; that call produced an
unadministerable board, so no legitimate workflow depended on it. The workspace
promotion keeps its existing response and now leaves qualifying boards' admin
roles intact instead of silently downgrading them.

This change spans 6 source files, above the "≤ 2 files" manual-contribution
guidance in CONTRIBUTING.md. Three are the substantive fix (the adapter routes,
the workspace writer, the new helper); the rest are the extraction that avoids
further copies of the same check. Splitting it would leave the duplication — and
the drift it caused — in place.

## New

- `server/extensions/board/api/members/lastAdmin.ts` —
  `wouldRemoveLastBoardAdmin(boardId, userId, nextRole, trx)` plus
  `enforceLastBoardAdmin()`, which runs a caller-supplied mutation inside a
  transaction under a per-board advisory lock and returns null when the change
  was refused. `enforceLastBoardAdminAcrossBoards()` offers the same guarantee
  for multi-board writers, locking board ids in sorted order so concurrent
  callers cannot deadlock. Also exports the two shared message constants.
- `tests/db/lastBoardAdminInvariant.ts` — PostgreSQL-backed proof covering what
  sequential fake-DB tests cannot: two admins demoted concurrently, two removed
  concurrently, a native demote racing a Trello-compat delete, the sequential
  sole-admin guards, and the workspace GUEST-conversion writer. Every assertion
  is read back out of SQL. Verified to fail — leaving the board with **zero**
  admins — when the advisory lock is removed while the transaction is kept, so
  the test demonstrates the lock is what closes the race.

The previous fake-DB fixtures for this invariant
(`__tests__/lastAdmin.test.ts`, `trelloCompat/tests/unit/lastBoardAdmin.test.ts`
and their fixtures) are removed: they asserted sequential behaviour that the
real-database proof now covers directly, and they could not model transactions.

## Technical Debt

The invariant is enforced in application code rather than by the database, so a
sixth writer to `board_members` would have to remember to use the helper. A
trigger or a deferred constraint asserting "at least one ADMIN per board" would
make it structural and remove that obligation entirely.

The advisory lock serialises all admin-count-sensitive writes for a board. That
is correct but coarse: two unrelated member changes on a busy board now queue
behind each other.

## What Should Be Done Next

- Add the database-level constraint described above, then reduce the helper to a
  friendly error path rather than the sole line of defence.
- Audit any future writer to `board_members` against this helper; the five
  current writers are covered.
- Consider whether the Trello-compat adapter should reuse the native handlers
  outright instead of issuing its own queries — the duplication here is what
  allowed those routes to drift from the invariant in the first place.
